# архітектура tMapOnline

у цьому документі пояснено, з чого складається tMapOnline і як ігрові дані потрапляють на карту в браузері. Python-сервіс отримує та зберігає дані. через API він передає їх вебкарті, а серверний мод збирає їх усередині tModLoader.

ланцюжок такий: Terraria передає відомості моду, мод надсилає їх сервісу, сервіс готує відповідь, а браузер перетворює її на карту й позначки. ні браузер, ні Python-сервіс не читають пам’ять процесу Terraria напряму.

коротко: мод читає гру, Python-сервіс отримує дані, браузер їх показує. API — це адреси для обміну даними між браузером і сервісом. snapshot — запис про стан гри в певний момент. кеш зберігає готові дані, щоб не створювати їх повторно.

## проєкти та межі відповідальності

```text
tMapOnline/                       # вебкарта, backend і мод
├── tmaponline/                  # Python-пакет і власний мод tModLoader
│   ├── backend/                 # запити, відповіді та статичні файли інтерфейсу
│   ├── telemetry/               # з’єднання з ігровим модом
│   ├── sprite_renderer/         # ігрові текстури та PNG-спрайти
│   ├── web/
│   │   ├── src/                 # редаговані вихідні файли інтерфейсу й карти
│   │   ├── assets/              # файли, створені під час збірки
│   │   ├── static/              # вихідні зображення, шрифти та інші ресурси
│   │   └── world-map/           # початкова HTML-сторінка карти
│   ├── tmodloader/
│   │   └── tMapOnline/          # вихідний код моду C# для сервера гри
│   ├── config.py                # читання, перевірка та типові значення YAML
│   └── runtime.py               # запуск і зупинка сервісу та гри
├── docs/                        # документація проєкту
├── tests/                       # автоматичні перевірки Python і вебкоду
├── tools/                       # команди збірки вебінтерфейсу й моду
├── config.example.yaml
├── package.json
└── pyproject.toml
```

`backend/http.py` обробляє браузерні запити й вибирає відповідь. `backend/store.py` надає іншим частинам програми спільний спосіб роботи з даними, не змушуючи їх знати, у яких файлах ці дані зберігаються. У `backend/services/` роботу поділено за темами: `player_history` — історія гравців, `movement` — переміщення, `live_telemetry` — актуальні ігрові дані, `monitoring` — стан сервера, `world_map` — карта.

Спільні формати й сталі значення зберігаються в `store_common.py`. Сховище складається з невеликих частин із чіткими завданнями, а не з одного великого класу. Блокування не дають двом задачам одночасно змінювати ті самі дані. Кеш повторно використовує нещодавно підготовлені результати.

У JSONL кожне повідомлення займає окремий рядок. Сервіс перевіряє його та перетворює на модель із `models/telemetry.py` — структуру з відомими полями. Так дані простіше використовувати, а помилки — знаходити. На межі програми дані перетворюються на формати, яких очікують браузер та інші клієнти.

Інтервали оновлення задаються в `config.yaml`, щоб рухомі позначки й велика карта не передавалися з однаковою частотою. tModLoader окремо надсилає позиції, сутності та кольорові дані карти. Між повідомленнями мод зберігає останнє значення кожної категорії.

Перший запит `/api/world-map` повертає метадані — розмір світу й опис доступних шарів — без піксельних чанків. Чанк — це прямокутна частина готового зображення. Повний JSON з усіма чанками можна явно запросити параметром `?tiles=0`, наприклад для експорту.

Браузер малює лише об’єкти у видимій частині карти. Для кожного видимого гравця чи об’єкта створюється HTML-елемент зі спрайтом. Коли карту переміщують або змінюють масштаб, браузер перераховує, які позначки залишити на екрані. Це змінює лише відображення: ігрові NPC від цього не з’являються й не зникають.

Зображення карти поділене на рівні піраміди: на віддаленому масштабі використовуються невеликі оглядові фрагменти, а під час наближення — детальніші. Сервер віддає PNG-плитки розміром до 256 × 256 пікселів і формує відповідь лише з чанків, що перетинають запитану ділянку. Кеш зберігає готові PNG, щоб не збирати їх повторно. Його обмежено кількістю записів і загальним обсягом 32 МіБ. У `/debug` видно влучання в кеш, витіснення та час підготовки зображень.

Canvas — поверхня браузера для малювання зображень. Одночасно активними залишаються не більш як 16 плиток карти та 4 МіБ декодованих зображень. Карта й маска дослідження розміщені на різних canvas, тому оновлення маски не змушує повторно завантажувати базові зображення. Після зміни рівня деталізації старе зображення залишається видимим, доки не надійде нове. Плитки за межами видимої області не додаються до DOM. Повний набір даних читається лише під час явного експорту.

Актуальні позиції, смерті, монети й зміни блоків надходять через `/api/world-map/live`. SSE (Server-Sent Events) залишає HTTP-з’єднання відкритим, щоб сервер надсилав нові повідомлення без окремого запиту для кожного об’єкта. Сервер надсилає дані поруч із видимою ділянкою та невеликим запасом, а браузер поновлює підписку після помітного переміщення карти. Шар монет запитується лише при сильному наближенні.

Коли блок змінюється, сервер зберігає оновлені дані. Браузер оновлює лише зображення плитки з цим блоком. Якщо координата кілька разів змінилася до наступного оновлення, використовується її останній стан. Інші плитки оновляться, коли користувач перейде до них. Панель `/debug` показує частоту й актуальність знімків, розмір відповіді та час підготовки зображень.

`telemetry/stream.py` приймає JSON-знімки, розділені символом нового рядка. Мод збирає стан сервера та надсилає його на localhost. Вебінтерфейс не звертається до ігрового процесу напряму, а читає узгоджений API.

### рендеринг спрайтів

`sprite_renderer/xnb_texture.py` перевіряє заголовки XNB і читає дані `Texture2D` у форматі RGBA. Стиснуті XNB розпаковує `sprite_renderer/lzx.py`, зокрема кадри 32 КіБ; зовнішній пакет LZX і Java runtime не потрібні. `PlayerSpriteRenderer`, `NpcSpriteRenderer` і `MapItemSpriteRenderer` компонують аватари гравців, портрети NPC/босів та іконки предметів. Pillow використовується лише на межі читання й запису PNG; кешування та HTTP-адреси зображень належать `StatusStore`. Мод tModLoader написаний на C#.

Щоб відтворити ігрові позначки, реалізацію звіряють із декомпільованим кодом тієї самої версії Terraria/tModLoader. Хрест смерті береться з ігрового ресурсу `Content/Images/MapDeath.xnb`; `Main.DrawPlayerDeathMarker` малює його за координатами `Player.lastDeathPostion`, по центру й з масштабом карти. Тому tMapOnline використовує оригінальний спрайт без додаткової тіні чи штучної обводки. Декомпільований код потрібен розробнику для перевірки поведінки гри; у репозиторії його немає, і для запуску проєкту він не потрібен.

### композиція та сервіси tModLoader

Потік телеметрії надсилає snapshot з інтервалом, налаштованим в ігрових тіках. Смерті фіксуються через `Player.KillMe`, отримують унікальний ID і залишаються в черзі моду, доки Python-сервіс не підтвердить успішний запис. Python застосовує налаштований TTL до збережених позначок. Напрямок гравців і NPC передається окремо від позиції, щоб інтерфейс міг повторити горизонтальне віддзеркалення спрайта з гри.

`TMapOnlineSystem` — корінь життєвого циклу та композиції: підключає ігрові хуки, створює сервіси й формує JSON-знімок, зберігаючи чинний контракт JSONL/API. Деталі делеговано об’єктам із вузькими обов’язками.

Корінь композиції створює інші об’єкти та з’єднує їх. Сервіс — допоміжна частина з одним завданням. Hook — точка, у якій гра викликає код моду у відповідь на подію, наприклад зміну світу.

- `TelemetryStreamServer` відповідає за TCP listener, клієнтів, JSONL, підтвердження snapshot і вхідні команди.
- `WorldMapScanner` сканує невеликий чанк базової карти за ігровий тик, готує палітру й повідомляє про прогрес.
- `PlayerMapChangeRevealer` будує відкриту ділянку біля гравця та обмежує повторне захоплення регіонів.
- `MapTileDataCapture` серіалізує ID блоків і стін та стискає ділянку.
- `MapTileNameCatalog` знаходить локалізовані назви блоків і стін та поступово надсилає їх разом із даними.
- `PlayerAppearanceSnapshotBuilder` збирає зовнішній вигляд гравця й експортує потрібні текстури.
- `WorldEntitySnapshotBuilder` збирає позначки пілонів, NPC/босів і викинутих монет.
- `BossProgressSnapshotReader` читає лише ванільні прапорці прогресу.
- `CalamityBossProgressAdapter` окремо запитує необов’язковий мод Calamity та його збережені прапорці.
- `BossVictoryTracker` зберігає повторні перемоги у форматі `ApplicationData/tMapOnline/boss-victories.json`.

Сервіси отримують лише потрібний їм стан. Читання та зміна `Main`, `Player`, `NPC`, тайлів, палітри й карти відбуваються синхронно в ігровому потоці. Фоновий транспорт отримує серіалізовані незмінні рядки JSONL, а не живі ігрові об’єкти. `Main.dedServ` не підмінюється для ініціалізації карти.

## структура вебінтерфейсу

`web/world-map/index.html` — єдина початкова сторінка вебкарти tMapOnline. `/` і `/world-map` відкривають ту саму карту; старий екран моніторингу вимкнений. Вихідні файли оболонки, карти, розділів і стилів містяться в `web/src`. `npm run build` компілює та мініфікує TypeScript в ES-модулі, а SCSS — у CSS у `web/assets`. У production Python роздає готові файли, Node.js не потрібен.

`src/app-shell.ts` містить `TMapOnlineApplication`: він завантажує дані розділів на запит і відкриває їх у піксельному діалозі. Карта одразу займає весь екран. `MapActionMenu` створює вертикальні категорії та сусіднє підменю; `PixelModal` відповідає за закриття, клавішу Escape і передачу клавіатурного фокуса. Гравці й маршрути налаштовуються у вікні гравців і відразу оновлюють шари карти. `MapZoomControls` з’єднує піксельні кнопки масштабу й огляд усього світу з контролером карти. Розділи `src/sections/{world,players,bosses,server,activity}.ts` завантажуються лише після відкриття відповідного пункту меню. Їхні стилі теж завантажуються за потреби.

Категорії карти містять керування гравцями й маршрутами, дані світу та перемоги над босами, стан сервера й активність; діагностика доступна також через `/debug`. Розділи можна вмикати в `site.sections`. Backend обслуговує їх через компактний `/api/section-data?section=...`. Дані про босів містять активних босів, ванільні прапорці перемог, сумісний лічильник повторних перемог і необов’язковий стан Calamity. Повний `/api/status` збережено для сумісності; модальні вікна його не використовують як джерело даних. Оновлення карти тривають, поки відкрите модальне вікно.

Інтерфейс використовує нативні ES modules без frontend runtime та бібліотеки компонентів. Межа завантаження явна: оболонка відповідає за меню й діалоги, SCSS розділу — за його піксельне оформлення, `mount(root)` — за запит і показ даних. esbuild і Sass запускаються під час розробки або пакування. Аналітика, історія гравців і журнали не завантажуються, доки користувач не відкриє відповідне вікно.

### об’єкти TypeScript та їхні обов’язки

`src/map/world-map.ts` залишається коренем композиції сторінки карти: вмикає налаштовані функції, з’єднує життєвий цикл даних із відображенням та оновлює шар карти. Окремі об’єкти відповідають за конкретні механізми:

- `MapSnapshotCache` — IndexedDB і відновлення збереженого стану.
- `MapChunkCodec` — розпакування та компонування базових чанків і оновлень.
- `MapPyramidLayerRenderer` — вибір рівня деталізації, завантаження видимих PNG-плиток, скасування застарілих HTTP-запитів після зміни області й пріоритет поблизу точки масштабування; без активної точки спершу завантажується центр viewport.
- `MapExplorationMask` — об’єднання імпортованої карти й маршрутів у маску відкритих ділянок.
- `MapImageExporter` — експорт піксельної карти у PNG з маскою дослідження, якщо її ввімкнено.
- `MapViewportController` — масштабування, переміщення, жести й події viewport; передає рендереру світові координати точки масштабування, щоб завантажити відповідні плитки першими.
- `MapZoomControls` — кнопки масштабу й повернення до огляду всього світу.
- `MapEntityLayer` — позначки гравців, NPC/босів, монет, пілонів і точки появи; координати поза екраном не створюють DOM-спрайти й цикли анімації.
- `MapTooltipController` — затримка наведення, кеш інформації про блоки й підказка.
- `MapPlayerPathService` — нормалізація історії гравців, кеш маршрутів і розділення дослідження на відрізки біля телепортацій.
- `MapRouteLayer` — SVG-маршрути та позначки поточних позицій.
- `MapDiagnosticsPanel` — стан сканера й діагностична панель.

Нову функцію карти додавай в окремий об’єкт із чіткою роллю та явними залежностями через конструктор або зв’язки. Не повертай кодек чанків, життєвий цикл IndexedDB, обробку жестів чи розмітку маркерів у `world-map.ts`. Великі сценарії карти виділяй, коли змінюєш відповідну функцію; не створюй тонкі класи-обгортки без власного стану чи поведінки.

Команди frontend: `npm ci` встановлює версії інструментів із lock-файлу, `npm run typecheck` перевіряє TypeScript, `npm run build` оновлює `web/assets`, а `npm run check:web` виконує обидві перевірки послідовно. Після змін вихідного коду збери assets до запуску або пакування tMapOnline. Python перевіряє Pyright у режимі `strict` (Pylance використовує той самий рушій): `npm run check:python`. Для локального середовища виконай `python3 -m pip install -r requirements-dev.txt`, потім `npm ci`. Повна перевірка — `npm run check:all`. У чотирьох наявних сервісах із гнучкими JSON-сховищами вимкнено лише діагностику невідомих типів; поля, що використовуються, усе одно перевіряються під час виконання, решта строгих правил Pyright лишається ввімкненою.

## стан і конфігурація

`config.yaml` керує запуском і доступністю сторінок та розділів. Тема браузера, вибрані гравці/шари й положення карти зберігаються окремо в `localStorage`. Персональні дані й кеші лежать у `~/Library/Application Support/tMapOnline`, а не в репозиторії. Схему API та телеметрії описано в [telemetry.md](telemetry.md).

Конфігурація відокремлює запуск сервісу від доступності сторінок і компонентів. Налаштування відображення користувача зберігаються окремо від серверних параметрів.
