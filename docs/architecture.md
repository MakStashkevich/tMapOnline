# Архитектура Terraria World Viewer

## Проекты и границы

```text
terraria-world-viewer/
├── terraria_viewer/
│   ├── backend/       # HTTP API/static hosting и фасад существующей модели данных
│   ├── telemetry/     # reconnectable JSONL client
│   ├── sprite_renderer/ # Python XNB/LZX reader and cached image renderers
│   ├── web/
│   │   ├── src/       # TypeScript, SCSS и разделённые frontend modules
│   │   ├── assets/    # собранные JS/CSS и скопированные статические спрайты
│   │   ├── static/    # исходные изображения интерфейса, копируются при сборке
│   │   └── world-map/ # HTML entry point
│   ├── sprite_renderer/
│   ├── config.py      # YAML schema/defaults/feature flags
│   └── runtime.py     # локальный lifecycle сервиса и игрового процесса
├── tmodloader/        # отдельный серверный мод, поставщик телеметрии
└── docs/
```

`backend/http.py` отвечает за API и границу HTTP. `backend/store.py` — стабильный фасад модели. Его доменные части находятся в `backend/services/`: `player_history`, `movement`, `live_telemetry`, `monitoring`, `world_map`. Общие файловые форматы и константы вынесены в `store_common.py`; mixin-срезы разделяют ответственность, но сохраняют один объект и единые locks/кэши. Входящие JSONL-снимки переводятся в dataclass-модели из `models/telemetry.py` для игроков, координат, NPC/боссов, монет и пилонов. Модели используются внутри доменной логики, а преобразуются в прежние словари только на границах хранения и HTTP. Это добавляет явные типы без изменения API и формата файлов.

`telemetry/stream.py` принимает newline-delimited JSON snapshots. Мод собирает состояние сервера и отправляет его на localhost. Web не обращается к игровому процессу напрямую: он читает согласованный API.

### Рендер спрайтов

`sprite_renderer/xnb_texture.py` проверяет заголовки XNB и читает их `Texture2D` RGBA-данные. Сжатые XNB разворачиваются через `sprite_renderer/lzx.py`, включая 32-КБ кадры; внешний LZX-пакет и Java runtime не нужны. `PlayerSpriteRenderer`, `NpcSpriteRenderer` и `MapItemSpriteRenderer` отвечают за композицию аватаров, портретов NPC/боссов и иконок предметов. Pillow используется только как лёгкая граница чтения/записи PNG; кэширование и HTTP-адреса изображений остаются у `StatusStore`. Мод tModLoader остаётся на C#.

Для соответствия игровым маркерам сверяемся с локальной декомпиляцией установленной сборки tModLoader в `/Volumes/T7/CodeProjects/Личное/_python/terraria-decompiled/tmodloader`. Крест смерти берётся из штатного `Content/Images/MapDeath.xnb`; код `Main.DrawPlayerDeathMarker` рисует его напрямую по `Player.lastDeathPostion` с центрированием и масштабом карты. Поэтому Viewer использует этот спрайт без дополнительной тени или искусственной обводки. Происхождение и команда обновления декомпиляции записаны в README рядом с ней; `terrex` к этой reference-копии не относится.

### tModLoader: композиция и сервисы

Поток телеметрии отправляет snapshot с конфигурируемой частотой игровых тиков. Смерти захватываются через `Player.KillMe`, имеют уникальный ID и остаются в очереди мода до подтверждения после успешной записи Python-сервисом. Python применяет настраиваемый TTL к сохранённым меткам. Направление игроков и NPC идёт в payload отдельно от позиции, чтобы UI мог повторить горизонтальное отражение спрайта из игры.

`TerrariaTunnelTelemetrySystem` — lifecycle/composition root: подключает игровые хуки, создаёт сервисы и собирает JSON-снимок, сохраняя прежний JSONL/API-контракт. Детали вынесены в объекты с ограниченной ответственностью:

- `TelemetryStreamServer` владеет TCP listener, клиентами и доставкой последнего полного снимка;
- `WorldMapScanner` сканирует базовую карту по небольшому чанку за игровой тик, готовит палитру и сообщает прогресс;
- `PlayerMapCapture` строит область карты возле игрока и ограничивает повторный захват регионов;
- `MapTileDataCapture` сериализует ID блоков/стен и сжимает область;
- `MapTileNameCatalog` разрешает локализованные названия и постепенно отправляет их вместе с данными;
- `PlayerAppearanceSnapshotBuilder` собирает внешний вид игрока и экспортирует нужные текстуры;
- `WorldEntitySnapshotBuilder` собирает маркеры пилонов, NPC/боссов и выпавших монет;
- `BossProgressSnapshotReader` отдельно читает прогресс ванильных боссов и Calamity, включая сохранённые флаги мира.

Сервисам передаётся только то состояние, которое нужно для их работы. Чтение и изменение `Main`, `Player`, `NPC`, тайлов, палитры и карты выполняется синхронно на игровом потоке. Фоновый транспорт получает сериализованные неизменяемые строки JSONL, а не живые игровые объекты. `Main.dedServ` не подменяется ради инициализации карты.

## Разбиение интерфейса

`web/world-map/index.html` — единственная точка входа Viewer. `/` и `/world-map` открывают одну карту; старый экран мониторинга выключен. Исходники оболочки, карты, разделов и стилей находятся в `web/src`. `npm run build` компилирует и минифицирует TypeScript в ES-модули и SCSS в CSS внутри `web/assets`. В production Python раздаёт готовые файлы и не требует Node.js.

`src/app-shell.ts` — объект `ViewerApplication`: он владеет навигацией, темой и ленивой загрузкой секций. Карта запускается сразу; модули `src/sections/{world,players,bosses,server,activity}.ts` импортируются динамически при открытии вкладки. Стили каждой вкладки также загружаются отдельно. Исходники стилей сгруппированы в `src/styles`: общие токены, базовые правила, компоненты, layout, карта и разделы. Тема сохраняется в localStorage и задаётся `data-theme` на корневом элементе; карта мира сохраняет свою игровую палитру, оболочка и разделы меняют светлую/тёмную тему.

Боковое меню содержит карту, игроков и историю игровых сессий, боссов и прогресс мира, состояние сервера, нагрузку и события. Слои исследования и маршруты игроков показываются только в разделе карты. Разделы можно включать в `site.sections` конфигурации. Backend обслуживает их через отдельный компактный `/api/section-data?section=...`; полноразмерный `/api/status` остаётся для совместимости и не используется как источник для интерфейса разделов. При смене раздела карта приостанавливает частое обновление, а при возврате обновляет карту и продолжает опрос.

UI использует нативные ES modules без frontend runtime и компонентной библиотеки. Граница загрузки явная: оболочка отвечает за навигацию, SCSS раздела — за его визуальные правила, `mount(root)` — за запрос и рендер данных. Сборка через esbuild и Sass выполняется при разработке/пакетировании; runtime-зависимости страницы отсутствуют. Это сохраняет лёгкий запуск карты и не загружает аналитику, историю игроков и журналы, пока пользователь их не запросит.

### TypeScript: объекты и обязанности

`src/map/world-map.ts` остаётся точкой сборки страницы карты: он активирует конфигурируемые функции, связывает жизненный цикл данных с отображением и обновляет слой карты. Отдельные объекты отвечают за изолированные механизмы:

- `MapSnapshotCache` — IndexedDB и восстановление сохранённого состояния;
- `MapChunkCodec` — распаковка и композиция базовых чанков и обновлений;
- `MapChunkLayerRenderer` — выбор только видимых чанков, управление canvas-кэшем и применение маски исследования;
- `MapExplorationMask` — объединение импортированной карты и маршрутов в маску открытых областей;
- `MapOverviewRenderer` — атомарная сборка обзорной миниатюры, восстановление из кэша и downsampling чанков;
- `MapImageExporter` — PNG-экспорт пиксельной карты с учётом включённой маски исследования;
- `MapViewportController` — масштабирование, перетаскивание, жесты и события viewport;
- `MapEntityLayer` — маркеры игроков, NPC/боссов, монет, пилонов и точки появления;
- `MapTooltipController` — задержка наведения, кэш информации о блоках и карточка подсказки;
- `MapPlayerPathService` — нормализация истории игрока, кэш маршрутов и разделение исследования на сегменты вокруг телепортаций;
- `MapRouteLayer` — SVG-маршруты и маркеры текущих позиций;
- `MapDiagnosticsPanel` — состояние сканера и диагностическая панель.

Новый функционал карты следует добавлять в отдельный объект с одной ясной ролью и явными зависимостями через конструктор/связи. `world-map.ts` не должен снова забирать на себя кодек чанков, жизненный цикл IndexedDB, обработку жестов или разметку маркеров. Оставшиеся крупные сценарии карты выделяются по мере изменения соответствующих функций; не создаём тонкие классы-обёртки без собственного состояния или поведения.

Frontend-команды: `npm ci` устанавливает закреплённый lock-файлом toolchain, `npm run typecheck` проверяет TypeScript, `npm run build` обновляет `web/assets`, `npm run check:web` выполняет обе операции подряд. После изменений исходников необходимо собрать assets до запуска или упаковки Viewer. Python-код проверяется Pyright в режиме `strict` (тот же движок использует Pylance): `npm run check:python`. Для локальной среды установите `python3 -m pip install -r requirements-dev.txt`, затем `npm ci`. Полная проверка — `npm run check:all`. В четырёх существующих сервисах с версионно-гибкими JSON-хранилищами отключены только диагностики неизвестных типов; используемые поля по-прежнему проверяются в рантайме, а остальной строгий набор Pyright включён.

## Состояние и конфигурация

`config.yaml` — конфигурация запуска, включения страниц и разделов. Клиентская тема, выбранные игроки/слои и положение карты хранятся отдельно в localStorage. Персональные данные и кэши остаются в прежнем каталоге TerrariaTunnel, не в репозитории. Схему API и телеметрии см. в [telemetry.md](telemetry.md).

Конфигурация отделяет запуск сервиса от включения страниц и компонентов; пользовательские настройки отображения хранятся отдельно от серверных параметров.
